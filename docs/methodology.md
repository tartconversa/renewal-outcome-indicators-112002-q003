# 跨项目成效分析方法说明

本文档规定系统如何把口径不一致的项目上报数字转化为可比较、可追溯、可复现的成效结论。
配套实现见 `src/renewal_analytics/`，合成数据情景见 `docs/input-contract.md`。

## 1. 四项必答属性

每期发布的每个数字都必须能回答：

1. **测量对象**：指标 ID 与定义版本（分子/分母概念），例如
   `I-01@v1 = open_facilities / planned_facilities`（开放口径）与
   `I-01@v2 = operating_facilities / planned_facilities`（实际运营口径）是两个不同指标。
2. **覆盖范围**：使用的边界版本、范围内设施清单，以及完整/待确认/缺失各有多少。
3. **数据成熟度**：交付类指标不做成熟度约束；居民结果类指标在设施开放后有
   2 个月成熟期（`MATURITY_LAG_MONTHS`），含未成熟设施的汇总显式标注，不与成熟项目直接比较。
4. **与前期比较的限制**：同口径同范围才给变化量；口径断裂或范围变化只标记、不解释差值。

## 2. 时间模型：一切以发布时点（as_of）为准

- 指标定义、边界按 `valid_from` 做 as-of 选择；**定义修订永不回写旧版期间的结论**。
- 观测按 `received_at` 可见性过滤：发布只采用 `received_at <= as_of` 的行。
- 同一（期间, 指标版本, 设施）的多条观测构成版本链，取发布时点可见的最新一条；
  后到的行登记为**迟到更正**，不删除旧行。
- 已发布报告因此天然可复现：给定相同输入文件与 as_of，输出字节级一致
  （由发布清单中的 SHA-256 指纹保证）。历史期被更正改变时，旧报告保持旧值，
  新报告在"迟到更正"栏说明原值→新值与来源行号。

## 3. 缺失不是零

每个设施单元格三态互斥：

| 状态 | 含义 | 对分子的影响 |
|---|---|---|
| `observed` | 有 complete 观测（含显式上报的 **0**）或带值的 corrected 行 | 按值计入 |
| `pending` | 已报但未确认（通常值为空） | 不计入，且阻断目标红绿判定 |
| `missing` | 期间内无任何观测 | 不计入；空单元格绝不解释为 0 |

目标判定再用里程碑区分两类缺失：

- **结构零**：里程碑证明设施在期间末仍未开放 → 零贡献可证实，不阻断判定；
- **无法解释的缺失**：设施已开放却缺观测，且指标分母是 scope 口径
  （设施必入分母、分子未知）→ 判定为"尚不可判断"。
- coverage 口径（分母本身就是"有完整观测的设施数"）自我归一化，
  缺失设施既不进分子也不进分母，不阻断判定，但覆盖率在报告中披露。

## 4. 分母变动：边界版本与设施合并

- 边界以版本化的 `boundary.csv` 表达；B1→B2 中 F-2 由 North 调整到 South、
  F-3 标注 `merged into F-1`，都通过边界版本体现，不修改任何历史输入行。
- 汇总的分母只数当前边界版本范围内的设施；跨期范围不同的趋势链接标记
  `SCOPE_CHANGE` 并列出退出/新增设施，变化量不予解释。

## 5. 验收 ≠ 运营

`accepted_on`（工程验收）与 `opened_on`（实际开始服务）分别计数。
引擎做双向证据交叉核对并写 `evidence_flags`：

- `ACCEPTED_BUT_NOT_OPEN`：已验收但期间末未开放（合成数据中的 F-2）；
- `OPEN_FACILITY_WITHOUT_OBSERVATION`：已开放却没有观测，提示数据缺口；
- `PENDING_OBSERVATION_EXCLUDED`：pending 行被排除在分子外；
- `REPORTED_BUT_FACILITY_IMMATURE`：未成熟设施已有上报值，仅作参考不参与判定。

## 6. 目标判定四态（优先级从高到低）

1. `INCOMPATIBLE_CALIBER`（数据口径不兼容）：目标绑定的定义版本与期间生效版本不一致，
   且第 7 节的回溯重算不可行。
2. `NOT_JUDGEABLE`（尚不可判断）：存在 pending、无法解释的缺失，或含未成熟设施。
3. `MET` / `BELOW_TARGET`（已达/未达目标）：口径一致、证据完整、成熟度满足后才允许红绿。

系统刻意不提供单一红绿总状态，每个判定都附中文理由。

## 7. 回溯重算（back-cast）的可行性闸门

口径切换后想把旧期间按新口径重算时，`concepts.backcast_feasible` 逐设施核查证据：

- 里程碑概念（如 `open_facilities`）要求每个设施都有开放日期，开放日未知即不可重建；
- 运营概念（如 `operating_facilities`）要求开放状态可判定 **且** 有完整使用量证据；
- coverage 分母要求范围内每个设施都有完整观测；
- 只有汇总观测、没有底层记录的概念（如 `monthly_visits`）一律不可回算。

任何一环证据不足就返回不可行及具体原因，旧期间只能保留旧口径并在报告注明，
杜绝把规划目标或新口径数字伪装成历史成果。

## 8. 血缘与发布物

- 每个 `Aggregate` 携带：定义版本、边界版本、范围设施、逐设施单元格、
  成熟度、证据标记和全部 `SourceRef（文件#L行号(主键)）`。
- `publish` 产出两份文件：
  - `report-<as_of>.md`：面向居民和决策者的中文报告；
  - `publication-<as_of>.json`：机器可读发布物，含输入指纹、逐值 `lineage`、
    目标判定、更正登记与投入—交付—结果链。
- 复现方式：保留输入文件与 as_of，重新运行同一命令，比对 SHA-256 即可。

## 9. 投入—交付—结果链

`chain_view` 按（期间 × 片区 × 工程类型）把三层证据并排呈现：
投入金额（同样受 `received_at` 可见性约束）、已验收数、已开放数、
有使用证据的运营数、已成熟数与范围设施数。三层口径互不替代，
"建成多少"不能代替"服务了多少人"。
